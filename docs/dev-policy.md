## 1. 何を作るか

**一言で**：工事現場の「建築計画のお知らせ」看板をスマホで撮ると、AIエージェントが内容を読み取り、区の届出データや地図で裏を取ったうえで、これから建つ建物（と消える建物）をPLATEAUの3D都市モデルの上に立ち上げ、住民に日影まで見せる。

**解決する苦痛**：街の変化を示す一番早く正確な情報が、現場のフェンスにしかなく、数字のままでは誰も実感できない。

| 誰が | 今の苦痛 | これで変わること |
|---|---|---|
| 近隣住民 | 「高さ25m」と言われても想像できず、日照や眺望の問題に気づくのが説明会や着工後になる | 自宅から見た大きさや日影を事前に3Dで確かめられる |
| 家を買う・借りる人 | 契約後に目の前に建物が建つ | 物件の周りで「これから建つもの」が見える |
| 自治体・学校・保育 | 人口の急増が後から分かる | 戸数を足し上げて世帯の増加を先に見込める |
| 3D都市モデル | 更新が数年おきで、変わる場所ほど古くなる | 着工前の確定値で「未来のPLATEAU」を作れる |

## 2. スコープ

| 項目 | 決定 | 理由 |
|---|---|---|
| 入力 | **現場の看板の写真だけ** | 時間、評価のしやすさ、話の分かりやすさ |
| 都市計画の資料（中目黒駅前北地区など） | 保留。余力があれば最後に1件だけ「看板が立つ前の段階」の見本として足す | 一般化すると工数が倍になる |
| 対象地域 | 目黒区（中目黒駅周辺を中心に撮影） | 届出データがCC BYで、住居表示まで載っている |
| 提供形態 | **Webまで**（ネイティブアプリは作らない）。公開URLは https://0319-2004.github.io/before-its-built/ （GitHub Pages、`main` への push で自動デプロイ） | 審査員がURLだけで触れる。3D表示もWebで動く |
| 解体の看板 | 既存のPLATEAUの建物を色分けして表示するだけ。対象の建物は、街区の中の候補から、階数・床面積（PLATEAUの階数×建築面積と比べる）と撮影地点のGPSで絞り、決めきれなければ「候補」として複数を薄く示す | 工数を増やさずに「消える建物」を見せられる。号の位置を座標にする手段（下記）がないため |

## 3. Metaのモデルの使い方

| 工程 | モデル | 決まっていること |
|---|---|---|
| 看板の検出 | SAM 3.1 | 枠だけ受け取り、**手元の元画像から高解像度のまま切り出す**。見つからなければ画像全体を看板として読む |
| 読み取り・検証 | Muse Spark 1.3 | 推論の強さは看板で`low`、手書きのある届出で`medium`。`store: false`。**`-contributor`の付いたモデルは使わない**（写真に個人名が写るため） |
| エージェント | Muse Spark 1.3 | 中心の軸（案B）。下のツールを呼びながら自分で検証する |
| 未来の街並み | Muse Image | 11/2以降に余力があれば（案C）。3Dのシルエットを参照画像にして写真を編集する |
| オープンウェイト | Muse Spark Open（Baseten経由） | 抽出の一部をこれでも動かし、精度を比較する。ボーナス賞の対象 |
| 使わない | Muse Wonder、Muse Glimmer、Voice Transcribe | 今回の流れに入れる場所がない |

### エージェントのツール

実装は `pipeline/agent.py`。モデルが次の手を選ぶループで、`process.py` の部品を包んでいる。

- `read_board()`：看板を読み取る（写真に看板が複数写っていれば何枚目かを選べる）
- `check_consistency()`：数値の矛盾をコードで確かめる。**確信度の低い項目も一緒に返す**
- `reread_fields()`：指定した項目だけを推論の強さ`medium`で読み直す
- `lookup_filing()`：区の届出データと照合し、足りない情報（住居表示など）を補う。
  **項目ごとの一致・不一致はコードが計算して返す**（モデルに数字を見比べさせない）
- `geocode()`：住居表示を街区の代表点に変える
- `extrude()`：建築面積と高さからボリュームを作る
- `request_retake()`：読めない項目があれば撮り直しを頼む
- `finish()`：結論を出して終える。`outcome`は`built`／`mismatch_notified`／`needs_review`の3つ
- 看板と届出が食い違った項目は、その項目だけを`reread_fields`で読み直し、それでも食い違えば根拠（地番、建物名など）を示して届出側の値を採るか、利用者に確認を頼む

**モデルは値を比べない。比べるのはコード**（§4）。`lookup_filing`が`normalize.py`を通した
うえで項目ごとの結果を返し、モデルはその結果に対して何をするかだけを決める。
`evaluate.py`と同じ規則を使うので、評価の数字と画面の判断がずれない。

### エージェントに置いたコード側の歯止め

モデルの判断に任せる部分が増えるほど、**任せてはいけないところをコードで止める**必要がある。

| 歯止め | 止めること |
|---|---|
| `extrude()`が軒高を弾く | 3D表示に軒高を渡してきたら、最高の高さ（なければ高さ）を使えと返す（一度やった取り違え） |
| `extrude()`が3D表示用の高さ以外を弾く | 読み取った値と違う高さを渡してきたら立てない |
| `extrude()`が確信度の低い項目を弾く | 高さ・建築面積の確信度が`0.9`未満なら立てない。読み直しても上がらなければ撮り直しを頼ませる |
| `lookup_filing()`が一致・不一致を計算する | モデルが数字を見比べて「だいたい同じ」と言うのを防ぐ |

**数値どうしの検算は「辻褄の合った嘘」を捕まえられない。** 遠い看板で、モデルが
「9階建てだから高さは30m台のはず」と桁を補い、`31.985m`（検算は通る）と書いた実例がある
（IMG_3966、確信度0.6、注記に「9階建てのため」と自分で書いていた）。
そこで**確信度の側でも止める**。境目の`0.9`は`read_board.py`の`LOW_CONFIDENCE`が正本で、
評価（§7）もそれを使う。

### 判断の記録

1枚ごとに `data/agent/<写真の名前>.json` に残す（**`data/`はリポジトリに入れない**）。
呼んだツール、入力、結果、モデルの短い理由（commentary のテキスト）、かかった時間を1手ずつ。
サンプルモード（§9）はこの記録を画面に流す。
届出の「建築物の名称」は照合の鍵・判断の根拠として記録には残るが、
公開する側へは出さない（「○○様邸」のように個人名が入りうる）。

## 4. 読み取りのルール

### スキーマ

- 各項目は `value` / `status` / `confidence` / `note` を持つ
- `status` は4つ：`read`（読めた）、`absent`（欄がない・空欄）、`unreadable`（読めない → 撮り直しの対象）、`masked`（伏せ字、記入例のみ）
- 高さは3つに分ける：`height_m`（高さ欄の上段の数値＝建築基準法上の高さ）、`max_height_m`（カッコ内の「塔屋等まで」＝最高の高さ）、`eave_height_m`（カッコ内の「軒高」）。3D表示は`max_height_m`があればそれ、なければ`height_m`。軒高は3D表示には使わない
- 高さの検算に「軒高 ≤ 高さ ≤ 最高の高さ」を足す（軒高を高さの箱に入れる取り違えを捕まえるため）
- 戸数が用途の欄にカッコ書きされている場合（例：共同住宅（4戸））は、`units`に入れて`use`からは外す
- 建築面積・延べ面積が2段書きなら、上段（今回の計画分）を取る
- 地番は`lot`にまとめ、筆のリスト、「の一部」（`partial`）、「ほか・外」（`has_others`）を持つ
- **住居表示は`address`に分けて持つ**（位置の主な手がかりになるため）。
  `raw`（欄の文字そのまま）、`chome`（町丁目）、`block`（街区番号）、`go`（号。なければnull）。
  看板では地名地番の欄に住居表示が併記されていることがあるが、`lot`とは必ず分けて取る
- データには出どころ（`source_type`：看板か都市計画か）を持たせる。「計画（看板）」と「上限（都市計画）」は画面でも区別する
- 構造は、木造・S造・RC造・SRC造・その他の5つにそろえる。元の文字は`raw`に残す。
  「木造(軸組)」は木造、「鉄筋コンクリート造一部鉄骨造」はRC造のように、
  **最初に書かれている構造を主な構造とする**
- 丁目の表記は漢数字にそろえる（「下目黒2丁目」→「下目黒二丁目」、「ヶ」「ケ」のゆれも吸収）。
  **「が丘」も「ヶ丘」に寄せる**（位置参照情報は「自由が丘」「緑が丘」「東が丘」、
  届出や看板は「緑ヶ丘」と書くことがあり、そろえないと街区の代表点が引けない）
- 看板の種類（`notice_type`）には`other`がある。工事現場には労災保険関係成立票や
  建設業の許可票も並んでいるため、**それを撮ったときは他の項目を読まず、
  「建築計画のお知らせを撮ってください」と返す**。全項目が`absent`になるだけでは、
  読めなかったのか別の看板なのかが区別できない
- **ほかの欄から逆算して数字を埋めさせない。** 階数や面積から辻褄の合う桁を決めるのは
  「読んだ」ことにならない。桁の一部が潰れていれば、その項目は`unreadable`にする。
  ほかの欄と合っているかはコードが確かめるので、モデルに合わせさせない
- **そろえる処理は`pipeline/normalize.py`の1か所にまとめる。**
  看板と届出を比べる前に必ずここを通す（同じ規則で両側をそろえないと精度が測れない）
- モデルが返すJSONは、`notice_type`が`other`の短い形のときに**閉じ括弧を落とすことがある**
  （実測）。`read_board.parse_json()`が**閉じ括弧だけを補って**読み直し、
  それでも読めなければもう一度モデルに聞く。中身は補わない（読めなかったものを
  「読めた」ことにしてしまうため）。補ったときは`json_repaired`の印を残す

### 個人情報

- 建築主・設計者・施工者・担当者の氏名、住所、電話番号は読み取らない・保存しない
- 写真と届出のPDFは`data/`と`samples/`に置き、リポジトリに入れない
- デモ動画で看板を映すときは名前の部分をぼかす
- マイマップなど共有する場所には建物の名称を入れない（「○○様邸」があるため）

### 検証の考え方

- **読むのはモデル、確かめるのはコード**
- 矛盾チェックの目的は、桁や小数点の大きな読み間違いを捕まえること。1階あたりの高さは**2〜10m**の広い範囲で判定する（用途ごとに細かく変えない）
- チェック項目：建築面積 ≤ 敷地面積、延べ面積 ≥ 建築面積、最高の高さ ≥ 高さ、延べ面積が建築面積×階数を大きく超えない
- 引っかかったものは「誤り」ではなく「要確認」として扱い、エージェントの判断材料にする
- 確信度は今はモデルの自己申告をそのまま使い、評価で「自信なしの項目ほど間違っているか」を確かめる。分かれていなければ2回読みなどを足す

## 5. 位置の決め方

**登記所備付地図の筆ポリゴンは使わない（主な手段にしない）**。目黒区は約8.2万筆のうち公共座標系が616筆だけで、残りは地図に重ねられない任意座標系のため。

| 順番 | 手がかり | やり方 |
|---|---|---|
| 1 | 看板に住居表示がある | 街区レベル位置参照情報で街区の代表点を取る |
| 2 | 看板に地番しかない | 届出データを地番で検索し、住居表示を引いてから1へ |
| 3 | どちらも使えない | 写真のEXIFのGPS、なければ撮影時のブラウザの現在地 |
| 検証 | 写真のGPS、地番の丁目 | 1・2で出た位置とGPSが離れすぎていないか、丁目が一致するかを確かめる |

- 建物の形：街区の代表点に、建築面積と同じ広さの正方形を置く。向きは周りの街並みに合わせる（`pipeline/orient.py`）。決め方は順に **(1) 敷地のPLATEAU既存建物の最小面積外接矩形 → (2) 最寄りの道路（`tran.geojson`）の縁 → (3) 近傍建物の多数派**、どれも無ければ北向き。どの方法で決めたかを `orientation_source` に残す。形・位置・向きとも近似であることを画面に明示する
- 位置の写真のGPSについて：iPhoneのブラウザから直接アップロードすると標準ではGPSが消えるが、**iPhone → Mac（iCloud写真・AirDrop）→ Macのブラウザからアップロード**なら残る。Macの写真アプリから「書き出す」場合は位置情報の項目をオフにしない

## 6. データ

### データを取る前に確かめる6つの観点

範囲（目黒区をカバーするか）、位置（地図に重ねられる座標か）、項目（必要な項目があるか）、鮮度（今に間に合うか）、ライセンス（公開リポジトリ・動画・デプロイで使えるか）、入手と形式（ログインや変換が要るか、Webで読めるか）。**取りに行く前に、この6つを満たすかを先に調べる。**

| データ | 状態 | メモ |
|---|---|---|
| 目黒区 標識設置届（中高層） | ✅ 取得済み・読み取り済み（R8年度の68件） | CC BY。週1回程度更新。地名地番・住居表示・設置日・高さ・階数・面積・着工・完了あり。**目視確認が未完了** |
| 目黒区 解体工事等標識設置届出名簿 | ✅ 取得済み・中身確認済み | 文字のPDF（表として読める）。令和7年度分と令和8年度分（2026-10-15時点）。場所は住居表示の「号」まで、構造・階数・床面積・工事期間あり。種類が「特定建設」だけの行は解体ではないので除外する |
| 街区レベル位置参照情報（目黒区、2025年版） | ✅ 取得済み | 出典を書けば無償。代表フラグ=1の点を使う。CP932。67/68件を座標化済み |
| 大字・町丁目レベル位置参照情報（目黒区） | ✅ 取得済み | 丁目の照合に使う |
| PLATEAU 公式配信（3D Tiles） | ✅ 表示確認済み | **表示はこれを使う**。目黒区は `13110-bldg-lod2-2025` 系（年度固定）、広域は東京都全域の tileset。3D Tiles 1.0・b3dm・Draco・CESIUM_RTC（LOD2はWebPも）で、NAVARA 0.2.1 で例外なく描画できた。CORS は親子とも `*`。SLAはないので、保険として公式の目黒区データ（LOD2テクスチャなし 33.5MB）を置き直せるようにしておく |
| PLATEAU の属性の当てにならなさ | ⚠️ 確認済み | `storeysAboveGround` は誤りがある（高さ30.8mの建物に「2階」）ので**高さからの推定と併用する**。`fireproofStructureType` は 耐火／準耐火造／その他 の3通りだけで SRC・RC・S を区別できず、「準耐火」は「耐火」を文字として含むので部分一致で見てはいけない。延べ面積は無い（`buildingRoofEdgeArea` ＝底面のみ）。住所は町丁目まで |
| PLATEAU（目黒区、2025年度版 CityGML） | ✅ 取得済み | 建築物LOD1は全棟、LOD2は一部。高さ・階数・用途あり。道路LOD1・LOD2あり。**建物の調査年は2021年**（それ以降に建った建物はなく、取り壊された建物は残っている）。PLATEAU GIS Converterで撮影ルートの4メッシュ（53393565・66・75・76）をGeoJSONに変換し、**サーバー側の計算専用**に使う（建物14,334件）。自前の3D Tiles（242MB）は表示には使わない。高さの欠測（measuredHeight=-9999、storeysAboveGround=9999）は、高さが欠測なら階数×3mで補い「推定」の印を付け、両方欠測なら計算から外す |
| 登記所備付地図 | 後回し | 公共座標系の616筆がどこかを見る程度 |

### 正解データ

- 届出をMuse Sparkで読み取った結果を、**全件目視で確かめてから**正解にする（モデルの出力をそのまま正解にしない）
- 目視は`uncertain`列がある項目を重点的に見る。確認済みの行は`verified`に`1`
- 分かっている読み間違いの例：15番の工事種別（実際は増築）、60番の住居表示（「1番」の可能性。モデルは「19番」と読んだ）。どちらもモデルが「自信なし」にしていた
- 看板の読み間違いの例：IMG_3928（届出No.51）の住居表示。看板には「3丁目17番」と書いてあるが「3丁目1番」と読んだ（写真で確認済み）。地番で届出を引けば17番と分かり、建物名「上目黒317」とも合う。エージェントの照合で直せる例としてデモと評価に使う

## 7. 評価

`pipeline/evaluate.py`が集計し、`docs/eval-summary.md`に件数と割合だけを書く。
写真ごとの詳細は建物名に個人名が入ることがあるので`data/eval/`に置き、リポジトリに入れない。

- 項目ごとの抽出精度（看板の読み取り結果 vs 目視確認した届出）
- 看板と届出の照合は、**地番（筆の番号）→ 住居表示 → 建築物の名称**の順に鍵を試す
- 届出は目視確認が済んだ行（`verified`）だけが正解なので、**確認済みと未確認を混ぜて出さない**
- 目視確認は`data/eval/verify.html`（照合できた行だけを並べた確認用のページ）で行う
- 位置の誤差（パイプラインが出した位置 vs 届出の住居表示の街区の位置、撮影地点のGPS）
- 確信度の当てになり方（自信なしの項目と、実際の間違いの重なり）
- Spark 1.3とSpark Openの比較、推論の強さ`low`と`medium`の比較
- 失敗例と限界を正直に書く（対象は中高層だけ、形は近似、延べ1万㎡超は区のリストにない、など）

## 8. 撮影

- 対象：完了予定がまだ先の届出。中目黒駅から1km以内の12地点のルート（マイマップに登録済み）を中心に、目黒駅近くの55番（16階）も
- 完了予定が2026年10月30日の26番は外す
- 60番は住居表示が1番か19番か、現地で両方の街区を見る
- 地図の点は街区の代表点なので、街区の周りを一周して看板を探す
- 1か所につき2枚：看板全体が読める近い写真と、敷地を含めた遠い写真
- カメラは位置情報オン、形式は「互換性優先」（JPEG）
- 目標30枚、最低15枚

## 9. Webの構成

| 部分 | 決定 |
|---|---|

## 10. 画面と表示のルール

- デモ画面：Design canvas「Before It's Built デモ画面」（夜の街の見た目。スキャン → 3D作成 → 地図 → 日影の4画面）
- 色：これから建つもの＝青、消えるもの・注意＝オレンジ。明るさでも区別できるようにする
- コンセプトは「PLATEAUと現実の差分」。画面はこの差分を最優先で見せる
- 旋回カメラ（サンプルモード）：エージェントが処理している間、敷地を中心にゆっくり旋回（約6°/秒）。画面を触れば止めて操作をユーザーに返す。`prefers-reduced-motion` と計測用 `fast` では回さない
- 置き換わりアニメ：**PLATEAUの古い建物そのものを消す**。公式3D Tilesは `featureUpdated` の評価で地物を `gml_id` ごとに `{show:false}` にでき（stage0と同じ仕組み）、既存建物を1棟だけ消せる。実輪郭に重ねたオレンジの箱を用意し、本物を `show:false` で消して灰→オレンジに切り替え、オレンジを地面へ沈めて消し、青い計画建物を立てる。本物が消えているので下から灰色は出ない。注意：NAVARAのベクタレイヤは追加〜表示に約2秒かかるので、切り替える前に `EXISTING_HOLD_MS` だけ待つ。件を替えたら消した建物を必ず戻す
- 日影：冬至、建物を直方体で近似、地上1.5mで計算。「法令上の日影規制の判定ではない目安」と必ず表示する
- 根拠のない数字（件数など）は画面に出さない

## 15. 判断の記録

| 判断 | 理由 |
|---|---|
| 看板だけに絞る | 入口を増やすとテストと評価が倍になり、デモの話もぼやける |
| 位置は住居表示が主、地番の筆ポリゴンは使わない | 目黒区の筆の大半が任意座標系で地図に重ねられない |
| エージェント化を軸にする | 「単純な画像分析アプリ」に見えないため。Best Agentic Use-Caseにもつながる |
| 矛盾チェックは広い範囲で | 用途ごとの基準より単純で、狙い（大きな読み間違いの検出）に合う |
| 確信度は自己申告のまま、評価で検証 | きれいな画像では正しかった。読みにくい画像で下がるかを実データで確かめる |
| Webまで | 審査員がURLだけで触れる。期間内に作れる |
| サンプルモードを作る | 海外の審査員は看板を撮れない |
| 変換はPLATEAU GIS Converter | 公式のOSSで、3D TilesとGeoJSONを1つのツールで作れる。誰でも同じ手順を再現でき、会社の環境を使わずに済む |
| 表示はPLATEAU公式配信 | 区全域・都全域を自前ホストなしで出せ、NAVARAで動作確認済み。自前の4メッシュより広く、見た目のインパクトも大きい。年度固定URLで再現性も保てる |
| 構造は5つの決まった値にそろえ、元の文字は残す | 看板の書き方が「木造」「木造(軸組)」「木造-一部鉄筋コンクリート造」と揺れるので、そのままでは届出と比べられない。元の文字を`raw`に残すので、そろえ方を間違えても後から直せる |
| そろえる処理は1つのファイルに集める | 看板側と届出側を違う規則でそろえると、精度の数字が揺れの分だけ悪く出る |
| 別の看板は`other`として撮り直しを頼む | 全項目が`absent`になるだけでは、看板が読めなかったのか対象外の看板なのかを区別できず、利用者に何を直せばいいか返せない |
| 評価は確認済みと未確認を分けて出す | 届出もモデルが読んだものなので、混ぜると「モデル同士の一致率」を精度と誤読する |
| 号レベルの住所検索は使わない | 国土地理院の住所検索APIは号まで返るが、利用条件が公開されておらず出典として書けない。アドレス・ベース・レジストリは公式ページで住居表示の位置までは整備途中とされており、今回は当てにしない |
| 表示と計算は gml_id でつなぐ | 公式3D Tilesのバッチテーブルと bldg.geojson の両方に同じ gml_id がある。住所はPLATEAU側が丁目までしかないので使えない |
| 高さの基準は楕円体高 | NAVARAも公式3D Tilesも楕円体高で描く。標高（_zmin）をそのまま地面にするとジオイド高（中目黒で約36.7m）だけ沈む。bldg.geojson のZをそのまま使う |
| 地面はGSI標高タイルを楕円体高にそろえて敷く | 地図を楕円体（高さ0）に貼ると、楕円体高の建物が地面から約46m浮く。GSIのDEM（`dem_png`）を地形に入れ、デコーダの `offset` にジオイド(+36.71m)を足して標高→楕円体高にそろえると地面が建物に合う。**落とし穴2つ**：(1) `offset` は**メートル**。epsilon(0.01)で割って36.71/0.01=3671を足すと地面が3671m持ち上がりカメラが空を向く。(2) `overscaledMaxZoom` は z14 タイルを**どのズームまで使い回すか**で、maxZoom と同じ14にすると近づいたとき z15/z16 を取りに行って404を量産する。高く（22）して使い回させる。遠景の粗いタイル（z5〜9）は海で欠けるので `minZoom=10`。実測は `docs/stage0.md` |
| PLATEAUの古さは隠さず見せる | 調査年が2021年なので、更地になった現場でも建物が残っている。これは「3D都市モデルは数年遅れる」という課題の実例として評価・動画で使う |
| 比べるのはコード、エージェントは次の手を決めるだけ | モデルに数字を見比べさせると「385.6 と 385.60 は違う」「71.87 と 70.32 はだいたい同じ」の両方が起きる。`lookup_filing`が`evaluate.py`と同じ規則で一致・不一致を出し、モデルはその結果に何をするかだけを決める |
| 確信度の低い読み取りでは建物を立てない | 検算は「辻褄の合った嘘」を捕まえられない。遠い看板でモデルが階数から高さの桁を補った実例があり、数値の整合だけでは素通りした。高さ・建築面積の確信度が`0.9`未満なら`extrude`が断る |
| 日影は自前で計算して地上1.5m平面に描く | NAVARAのCSM影は3Dジオメトリの上にしか落ちず、更地の計画地には1枚も映らない。直方体の影を自前で出せば更地でも必ず出て、§10の「地上1.5mで計算」にも合う。シーンの光（CSM）は同じ冬至時刻に合わせ、既存建物には本物の影も付ける |
| モデルの壊れたJSONは閉じ括弧だけ補う | 中身を補うと読めなかったものが「読めた」ことになる。補えなければもう一度聞き、それでも駄目なら**ツールの失敗として返す**（「写真が悪い」と誤って結論させないため） |
| エージェントの終わり方を4つに決める | `built`／`mismatch_notified`／`needs_review`／`needs_retake`。画面の出し方と評価の数え方をこの4つに揃える |
